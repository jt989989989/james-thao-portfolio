05 — How I Work

Plan it. Build it.
Test it. Ship it.

Whether it's a game level or an automation flow, I work the same way: understand the problem first, build the smallest version that works, then improve it in the open.

1

Plan

Break the task down: what should it do, what does “done” look like, and what's the smallest version worth building?

2

Design

Sketch the flow before writing code — screens, states, and edge cases — so the build has a map to follow.

3

Build

Build in a branch, test it like a user would, and show the work before anything goes live.

4

Ship & improve

Launch it, play-test it, fix what breaks, and keep tightening. A project you don't revisit stops improving.

For employers & collaborators

How I work in GitHub

I work the way a team works: pull the latest, branch for the task, commit with a clear message, push, and open a pull request for review. I don't edit main directly. It's all public: my portfolio repo holds 18 projects — security tools, games, and utilities — each with a README and passing tests, so the commit history shows the work as it happens.
